# AG Grid: конспект для технического интервью

## Как представлять проект

«Это локальная IoT-консоль с четырьмя сценариями. Текущее состояние устройств обновляется транзакциями, история загружается блоками, конфигурация редактируется с доменной валидацией, аналитика показывает агрегированный срез. Для каждого сценария выбран свой поток данных, а не один универсальный способ работы с таблицей».

Не представляйте mock как настоящий backend, а локальные диагностические числа — как универсальный benchmark. Все данные синтетические. Seed 42 делает значения воспроизводимыми; Live использует текущее время для lastSeen. Battery означает процент израсходованного заряда: большее значение хуже.

## 1. Live Telemetry

**Что реализовано.** Текущий парк из 100, 1 000 или 10 000 устройств. Можно менять интервал и количество обновлений, включать периодические burst, останавливать поток, сбрасывать данные, искать по всей таблице и менять колонки. Меняются value, status и lastSeen; отображение подсвечивает обновлённые значения.

**Почему Client-Side Row Model.** Полный набор текущих состояний ограничен и доступен в памяти. Это не история всех событий: на устройство приходится одна актуальная строка. Grid может сортировать и фильтровать весь парк без запроса к серверу.

**Основные API.** `columnDefs`, `defaultColDef`, `getRowId`, `getRowNode`, `applyTransactionAsync`, `flushAsyncTransactions`, `quickFilterText`, `enableCellChangeFlash`, события Grid State. В `features/live-telemetry/columns.ts` удобно искать конфигурацию колонок.

**Поток обновления.** Timer выбирает устройства детерминированно, получает актуальную строку по ID, создаёт новый объект только для изменённой строки и отправляет массив `update`. `rowData` не заменяется целиком на каждом tick. AG Grid объединяет работу в окне 50 мс. При смене нагрузки или размонтировании timer очищается; pending grid updates учитываются отдельно от входящего потока.

**Что решает подход.** Стабильные ID сохраняют связь между устройством и RowNode после сортировки. Batch снижает количество повторных проходов и отрисовок. React не должен рендерить весь экран для каждого сенсорного события.

**Trade-offs.** Все актуальные строки остаются в памяти; клиентская сортировка и фильтрация всё равно имеют стоимость. Batch добавляет небольшую задержку. Слишком тяжёлый renderer может испортить результат даже при правильных transactions. Частота входящих событий и частота React-обновления диагностических карточек — разные величины.

**Альтернативы.** При редких изменениях достаточно обычной `applyTransaction` или immutable `rowData` с ID. Настоящий поток потребует WebSocket/SSE, reconnect, дедупликацию, ordering и backpressure. Если входной поток быстрее интерфейса, можно хранить последнее событие на устройство до очередного batch; это продуктовый выбор, поскольку промежуточные состояния будут пропущены.

| Вероятный вопрос                                   | Короткий ответ                                                                                                                                |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Почему не `setRows(rows.map(...))` на каждый tick? | Это проход по всему массиву и новый prop при каждом обновлении. Когда известен небольшой набор изменений, transaction точнее выражает работу. |
| Что произойдёт после сортировки?                   | Обновление найдёт строку по `id`, а не по её экранной позиции. Grid пересчитает порядок согласно модели.                                      |
| Нужен ли `useMemo` для каждого значения?           | Нет. Стабилизируем объекты и функции, передаваемые grid, когда смена ссылки запускает лишнюю работу. Примитивы сравниваются по значению.      |
| Почему число received может отличаться от applied? | Есть асинхронная очередь. Метрики входа и успешного применения относятся к разным этапам. Их нужно измерять и называть отдельно.              |
| Можно обещать 60 FPS на 10 000 строк?              | Без измерения на целевом устройстве и нагрузке — нет. Виртуализация и batching уменьшают стоимость, но не дают универсальную гарантию.        |

## 2. Historical Logs

**Что реализовано.** 10 000, 100 000 или 500 000 виртуальных измерений; блочная загрузка, задержка, принудительная ошибка, retry, фильтры, сортировка, очистка cache, approximate position jump и request inspector.

**Почему Infinite Row Model.** Нужна плоская история большого размера и рабочая Community-редакция. Grid запрашивает блоки по мере прокрутки, а datasource определяет состав и порядок строк. Пользователь не должен ждать загрузки всей истории для первой страницы.

**Основные API.** `rowModelType='infinite'`, `IDatasource.getRows`, `IGetRowsParams`, `successCallback`, `failCallback`, `cacheBlockSize=200`, `maxBlocksInCache=8`, `maxConcurrentDatasourceRequests=2`, `purgeInfiniteCache`, `ensureIndexVisible`. Колонки находятся в `HistoricalLogs.tsx`, вычисление запроса — в `query.ts`, lifecycle запросов — в `datasource.ts`.

**Границы запроса.** `startRow` включается, `endRow` не включается. Для `[0, 200)` ожидается до 200 строк. Во второй аргумент `successCallback` передаётся известное итоговое количество: для 250 строк — 250, а не 249. В запрос входят `filterModel` и `sortModel`.

**Правильный порядок.** Сначала фильтруем логический dataset, затем сортируем его, затем берём диапазон. Если отсортировать только загруженный блок, первая страница не будет содержать глобально минимальные/максимальные значения. Quick Filter здесь не используется: он предназначен для клиентского полного набора.

**Локальная реализация.** `telemetryAt(index)` создаёт запись по индексу. Без фильтра/сортировки создаются только строки блока. Для сложного запроса сканируем виртуальный набор, сохраняем компактные индексы совпадений и временные скалярные ключи сортировки. Cooperative merge sort и scan периодически возвращают управление браузеру. Это main-thread работа, не Worker и не сервер.

**Параллельность.** Запросы блоков 0–200 и 200–400 могут быть одновременно правильными. Поэтому глобальный «применить только последний requestId» неверен. Отменяется поколение старого запроса после смены фильтра/сортировки, а блоки актуального поколения разделяют promise одного индекса. Destroy отменяет timer и работу. Inspector ограничен по размеру.

**Trade-offs.** Infinite кеширует только блоки строк, но mock-индекс всё равно имеет O(N) стоимость памяти/сканирования; сортировка — O(M log M) для M совпадений. Cooperative yielding позволяет обрабатывать UI между порциями работы, но не уменьшает асимптотику и добавляет scheduling overhead. Точный total в реальной БД может быть дорогим.

**Альтернативы.** SSRM нужен для серверных групп, агрегатов и pivot; он Enterprise. При маленькой истории возможен Client-Side. Worker убрал бы тяжёлые локальные вычисления с main thread, но потребовал бы отдельного протокола сообщений и отмены. В реальном продукте предпочтительнее backend с time windows и pagination tokens.

| Вероятный вопрос                              | Короткий ответ                                                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Это настоящий server-side filtering?          | Grid делегирует запрос datasource, но в демо его исполняет браузер. Архитектурный контракт похож на API; физическое место вычислений другое.           |
| Что отправлялось бы Node.js?                  | Временной диапазон, разрешённые поля/операторы фильтра, sort, размер блока и continuation information. Сервер обязан валидировать DTO.                 |
| Как связать это с Timestream?                 | Backend переводит DTO в ограниченный запрос, нормализует результат и работает с токенами продолжения. Произвольный offset не стоит считать бесплатным. |
| Зачем проверка поколения, если есть abort?    | Abort полезен для прекращения работы, но late response всё равно должен проверяться перед применением.                                                 |
| Как работает retry?                           | Cache очищается, grid снова запрашивает нужные блоки. Нужно выключить принудительную ошибку, иначе retry закономерно снова упадёт.                     |
| Можно агрегировать все строки через Grid API? | У Infinite в браузере только часть данных. Для полного результата агрегирует backend или отдельный полный query, а не текущий cache.                   |

## 3. Device Configuration

**Что реализовано.** Текстовый, числовой, select и checkbox editors; dirty rows, список изменений, Save/Revert selected/all, добавление и подтверждаемое удаление, undo/redo cell edits. Ошибка save не уничтожает draft. Configuration остаётся смонтированной после первого посещения, поэтому draft переживает переключение вкладок.

**Почему Client-Side Row Model.** Редактируется небольшой полный список конфигураций. Нужны локальная проверка, выделение и сравнение с baseline без сложной distributed-edit модели.

**Основные API.** `editable`, `cellEditor`, `valueParser`, `valueSetter`, `onCellValueChanged`, `cellClassRules`, `rowClassRules`, `rowSelection`, `getSelectedRows`, `stopEditing`, `undoRedoCellEditing`, `undoCellEditing`/`redoCellEditing` и Grid State. Колонки — `features/device-configuration/columns.ts`, правила — `model.ts`.

**Ответственности.** Formatter не изменяет значение. Parser превращает input в число/строку. Validator проверяет весь candidate device. Setter применяет корректное изменение. Save переносит snapshot в baseline только после успеха. Dirty сравнивает draft с независимой сохранённой копией.

**Правила.** Имя непустое, до 80 символов; sampling — целое число 1–3 600 секунд; пороги конечные и `warningThreshold < criticalThreshold`. Некорректный candidate отклоняется setter, сообщение объясняет причину. Save повторно использует доменную валидацию.

**Почему pessimistic save.** Изменения уже видны как draft, но «сохранено» показывается только после подтверждения. На время simulated request операции ограничены, чтобы snapshot не затёр более позднюю правку. При ошибке baseline не меняется и draft остаётся доступным. Это проще, чем optimistic rollback с конкурентными правками.

**Удаление и undo.** Удаление после подтверждения сначала staged; Save all фиксирует его, Revert all возвращает строку. Grid undo — история cell edits, а Revert — восстановление относительно бизнес-baseline. Это разные механизмы. Сортировка, фильтрация и замена rowData очищают native undo. Сохранённые в mock данные исчезают после reload — backend отсутствует.

**Альтернативы.** `readOnlyEdit` + `onCellEditRequest` подходят, если владельцем изменений является внешний store; тогда native undo не выполняет операции автоматически. Для реального API понадобятся версии записи/ETag, конфликт-диалог и серверная валидация. Full-row editing помогает изменять связанные поля одним действием; cell editing проще для демо, но порядок изменения порогов имеет значение.

| Вероятный вопрос                                              | Короткий ответ                                                                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Почему проверка не только в editor?                           | Editor можно обойти другим путём изменения данных. Доменное правило должно применяться независимо и перед save.                               |
| Почему нельзя хранить draft и baseline одним объектом?        | Grid меняет draft; общая ссылка изменит baseline тоже, и dirty станет ложно чистым.                                                           |
| Что если пользователь правит во время save?                   | Здесь редактирование ограничено до завершения. Для конкурентного сценария нужно сохранять версию snapshot и не стирать последующие изменения. |
| Warning сейчас 35, нужно 50, critical сейчас 42 — что делать? | Сначала увеличить critical, потом warning. Альтернатива — full-row edit с проверкой согласованной пары.                                       |
| Это полноценный Excel?                                        | Нет. Cell editors и undo доступны, но multi-cell clipboard, ranges и fill handle требуют Enterprise.                                          |
| Как вернуть только часть изменений?                           | Revert selected восстанавливает выбранные IDs из baseline; остальные drafts сохраняются.                                                      |

## 4. Analytics

**Что реализовано.** Фиксированный детерминированный sample из 10 000 измерений агрегируется по location + type + unit. Показываются count, min, max, avg и доля warning/critical, отдельная HTML/CSS диаграмма, автоматическое состояние колонок и ручное Save view/Restore view.

**Почему Client-Side Row Model.** На вход grid приходят уже небольшие summary records. Фильтрация summary-строк не пересчитывает исходную историю. Это аналитический preview, а не интерактивный query builder.

**API.** Обычные `rowData`, `ColDef`, formatter, сортировка/фильтры и Grid State. Native `rowGroup`, `aggFunc`, `pivotMode`, `sideBar` не включены.

**Trade-offs и альтернативы.** Community baseline работает без ключа; группировки вычисляет приложение. Для динамического drag-and-drop grouping и pivot стоит использовать Enterprise. Для огромного history агрегирует backend. Среднее нельзя считать между разными единицами. Среднее средних групп тоже некорректно без весов count.

| Вероятный вопрос                       | Короткий ответ                                                                                                                            |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Почему нет встроенного pivot?          | Это Enterprise. Для цели демо выбран явно обозначенный Community summary, а extension документирован.                                     |
| Avg относится ко всем 500 000 записям? | Нет, только к указанному sample из 10 000. Область расчёта показана явно.                                                                 |
| Почему отдельный unit в ключе группы?  | Числа разных единиц нельзя складывать и усреднять без преобразования.                                                                     |
| Что изменится при серверной аналитике? | UI отправляет group dimensions и разрешённые агрегаты, backend возвращает summary DTO. Потребуется договориться о time window и точности. |

## Ключевые понятия AG Grid

### `field`

Имя свойства row data, из которого grid читает значение. Например, `{ field: 'samplingInterval' }` связывает колонку с данными. Поддерживается nested path вроде `address.city`. `headerName` отвечает только за заголовок. `colId` нужен для устойчивой идентификации колонки, особенно если `field` отсутствует или повторяется.

### `valueGetter`

Вычисляет значение колонки из строки/контекста, когда простого field недостаточно. Например, разность critical и warning. Возвращать лучше настоящее число, а не форматированный текст. Getter должен быть чистым: без setState, fetch и изменения data. Его могут вызывать чаще, чем ожидается. Он не заменяет dedicated grouping/aggregation API.

### `valueFormatter`

Возвращает текст для отображения значения: округление, дата, единицы. Исходное число остаётся числом. Для числовой сортировки это существенно: строка `"100 kPa"` не эквивалентна числу 100. Formatter должен нормально обрабатывать отсутствующее значение; в некоторых контекстах params.data отсутствует. Общие `Intl` formatter экземпляры дешевле, чем создание их на каждую ячейку.

### `cellRenderer`

Отвечает за представление сложнее текста: status badge, кнопку, небольшую структуру DOM/React. Здесь status renderer создаёт простой элемент с текстом и классом. Если достаточно текста, используйте formatter. Renderer не должен становиться владельцем бизнес-данных, делать запрос на каждую ячейку или интерполировать непроверенную строку в HTML.

### `cellEditor`

UI, активный во время редактирования. Тип editor выбирается по данным: число, текст, boolean или список. Renderer и editor — разные роли. Числовые, select и checkbox поля используют штатные Community editors. Имя редактируется небольшим React-компонентом `NameEditor.tsx`: `CustomCellEditorProps`, `onValueChange`, `parseValue` и `useGridCellEditor` показывают React-интеграцию и validation callbacks. Локальный текст сохраняет пробелы при вводе; в grid передаётся parsed draft. Basic Select не равен Rich Select; последний Enterprise.

### `valueParser`

Преобразует введённое значение перед записью. Например, строку `'12'` в число 12. Пустая числовая строка не должна незаметно становиться допустимым нулём. Parsing отвечает за преобразование, но сам по себе не доказывает допустимость sampling interval или пары порогов.

### `valueSetter`

Принимает решение о записи. В стандартном режиме grid умеет записать `field` сам; setter полезен для контроля, cross-field validation или нестандартного хранения. Возвращает `true`, если данные реально изменились, `false`, если изменение отклонено или ничего не поменялось. В демо сначала собирается candidate, проверяется доменной функцией, затем обновляется draft.

### `getRowId`

Чистая функция, возвращающая уникальный стабильный string ID строки. Display index не подходит: сортировка и фильтрация меняют позицию. Нельзя генерировать новый UUID при каждом вызове. Для history уникален ID записи, а не deviceId: одному устройству соответствует много измерений.

### Transactions и `applyTransactionAsync`

Transaction описывает `add`, `update`, `remove`. `applyTransaction` выполняет работу синхронно; `applyTransactionAsync` ставит её в batching queue и возвращает результат через callback. Grid может обработать несколько обновлений вместе. `flushAsyncTransactions` нужен, если следующая операция требует уже применённых данных. Batching — не то же самое, что debounce с потерей промежуточных значений: семантику объединения входящих событий определяет приложение.

### Row Models

| Модель      | Где полный набор                         | Кто фильтрует/сортирует                        | Когда подходит                                                    |
| ----------- | ---------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------- |
| Client-Side | В браузере                               | Grid                                           | Ограниченная текущая таблица, редактирование, небольшие summaries |
| Infinite    | Обычно backend, в браузере cache блоков  | Datasource/backend                             | Большая плоская история в Community                               |
| Server-Side | Backend; клиент хранит загруженные части | Backend с дополнительными возможностями модели | Серверные группы, агрегаты, pivot; Enterprise                     |

Название Client-Side не запрещает изначально загрузить данные через HTTP. Название Infinite не означает бесконечную БД. SSRM не является обязательным условием любого server-side fetch.

### DOM virtualization

В DOM находятся видимые строки/колонки и небольшой буфер. Остальные данные могут быть в памяти модели без DOM-элементов. Это уменьшает стоимость rendering, но не делает бесплатной сортировку 500 000 объектов. Отдельно обсуждайте объём dataset, cache модели и число DOM nodes. Отключать virtualization ради простого теста production-кода не следует.

### Filtering и sorting

В Client-Side grid знает полный набор. В Infinite filter/sort model отправляется datasource. Number filter сравнивает числа, text filter — текст. `filterParams.debounceMs` снижает количество запросов при вводе. В mock поддерживаются используемые text/number операторы и составные AND/OR; это не полный SQL/query language.

### Grid State

Это пользовательское представление таблицы: порядок/ширина/видимость/pinning колонок, sort и filter. `initialState` читается один раз; `stateUpdated` и `gridPreDestroyed` дают state для сохранения. `setState` предназначен для восстановления, а не controlled-grid цикла на каждом React render. В приложении сохраняются только нужные разделы с runtime validation. Reset State не должен уничтожать dataset.

### React memoization

`useMemo` сохраняет ссылку на `columnDefs`/объект настроек; `useCallback` — на callback, если ссылка важна для Grid Options. Модульная константа ещё проще для действительно статической конфигурации. Неправильный dependency array создаёт stale closure. Не все события требуют memoization, а стабильная ссылка не исправит дорогое вычисление внутри функции. Проверяем profiler/измерениями, а не количеством `useMemo`.

### Community и Enterprise

Community покрывает основные row models данного демо, rendering, editing, сортировку, обычные фильтры, состояние, virtualization и native cell undo. Enterprise добавляет grouping/aggregation, pivot, SSRM, ranges, grid clipboard, tool panels и integrated visuals. Реальный выбор зависит от нужного UX и лицензии. Полный список с официальными ссылками находится в [FEATURE_MATRIX.md](FEATURE_MATRIX.md).

## Перед созвоном

Запустите `npm ci`, `npm run dev` и откройте файлы колонок. Проверьте edit → failed save → successful save → revert, history filter → sort → retry, live pause и восстановление колонок после reload. Подготовьте объяснение одной строки от generator до DOM. Затем выполните [практические упражнения](LIVE_CODING_TASKS.md) и проговорите [английские фразы](INTERVIEW_PHRASES_EN.md).
